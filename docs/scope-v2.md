# TV Tracker — v2 Scope

Builds on `docs/scope.md` (v1) and `docs/technical-design.md`. Read those first —
this doc only covers what changes.

## Overview

v1 was a single-user proof of concept for one person. **v2 has exactly two
goals: accounts, so friends/family can each track privately, and a PWA, so it
installs to a phone's home screen.** Everything else that was previously
listed under "Phase 2" in `scope.md` — movies, ratings, notes/reviews, a stats
dashboard, notifications — is **not** part of v2. It stays captured as a future
idea; nothing here builds toward it.

## Decisions made for v2

- **Login method: anonymous account-code**, not Google OAuth. A code *is* the
  account — no email, no PII, consistent with v1's "collects no personal data
  at all" stance. Traded off deliberately against Google OAuth's easier build
  and built-in recovery: this is a closed group of friends/family, not public
  signup, so self-serve recovery matters less than staying data-minimal.
- **Mobile: a PWA**, not a native app. Reuses the existing Next.js codebase and
  server actions entirely — no second codebase, no app store account, no
  native API layer to build. Native (React Native/Expo) was considered and
  rejected for this project's scale: it would mean maintaining two codebases
  indefinitely for a handful of users, which cuts against the "minimal moving
  parts" reasoning `scope.md` already uses to justify the rest of the stack.
- **Nicknames are required and unique**, chosen on first login. v2 itself has
  no profile page and no way to find another user by nickname — that's future
  scope (see "Ideas for the Future"). The nickname is captured and
  uniqueness-enforced now anyway, specifically so that future feature doesn't
  need a backfill or a forced-rename migration later, the same reasoning
  `AGENTS.md` already applies to any column: collect it at the point of
  creation, not after the fact.

## Features (v2 — build this)

1. **Account-code login** — enter a code, get a private session. No signup
   form; codes are generated by the admin (Théodore) and handed out directly,
   the same way `APP_PASSWORD` is generated and shared today.
2. **First-login nickname** — the first time a code is used, the account can't
   proceed into the app until a unique nickname is chosen: 3–12 characters,
   letters/numbers plus a small set of special characters, case-insensitive
   for uniqueness. **Permanent — cannot be changed once set** (renaming is on
   the roadmap, not in v2), so the picker UI needs to make that clear before
   the user confirms. It's what will show on a future profile page and what
   other users will search by, once social features exist — see the
   technical design doc for why it's collected now rather than later.
3. **Per-user data** — `TrackedShow`, `WatchedEpisode`, and `Settings` become
   scoped per account. Two people tracking the same show don't see or affect
   each other's progress. The `Show`/`Episode` TMDB cache stays global/shared —
   there's no reason to fetch and store the same show twice.
4. **Logout**
5. **Installable PWA** — manifest + icons + service worker so the app installs
   to a phone's home screen, launches full-screen (no browser chrome), and
   shows a splash screen.

### User Stories (v2)

- As an account holder, I want to log in with my personal code so my tracking
  data is private to me.
- As a new account holder, I want to pick a unique nickname the first time I
  log in so I have an identity in the app beyond an opaque code.
- As the admin, I want to generate a new code for a friend/family member so
  they can start using the app without me touching their data.
- As a user, I want my session to persist across visits so I don't have to
  re-enter a long code constantly.
- As a user, I want to log out from a device that isn't mine.
- As a user, I want to install the app to my phone's home screen so it feels
  like a normal app instead of a browser tab.

### Success Criteria (v2 "done")

Two or more people can each log in with their own code, are required to set a
unique nickname before reaching the rest of the app on first login, use the
app entirely independently with zero data crossover, and install it to a
phone's home screen with a working icon, name, and full-screen launch — on
both iOS Safari and Android Chrome, tested on real devices, not just a desktop
browser's device emulator.

### Non-Functional Expectations (v2)

- Still small-scale: a handful of trusted users, not public signup at any
  point.
- **No account recovery.** Losing a code means losing the account. This is an
  accepted trade-off of staying anonymous/data-minimal, not an oversight — say
  so to anyone you hand a code to.
- Offline support is partial, not full. See the technical design doc — most
  pages are `force-dynamic`, so a service worker can cache the app shell but
  not real watch data. Don't advertise "works offline."
- Concurrent writes from multiple users are assumed fine on Turso's free tier
  at this scale (a handful of people, not load-tested) — worth re-checking if
  the group ever grows materially.

## Explicitly Out of Scope (for v2)

- Public sign-up / self-serve account creation — codes are always
  admin-generated and shared out of band
- Native mobile app (React Native/Expo or otherwise)
- Push notifications — the PWA groundwork doesn't preclude this later, but it
  isn't being built now
- Recovering a lost account code
- A profile page, or any way to find/search for another user by nickname —
  v2 only collects and uniqueness-checks the nickname, it doesn't build
  anything that displays or searches it yet
- Everything from v1's old "Phase 2" list that isn't accounts or PWA: movies,
  ratings, notes/reviews, profile/stats dashboard, notifications — see "Ideas
  for the Future" below

## Ideas for the Future (not scheduled, not v2)

Carried over from `scope.md`'s old Phase 2 list, now explicitly deferred past
v2:

- Movies (search, tracking, watchlist)
- Ratings — 1–5 per show/movie
- Notes/reviews per episode or show
- Profile page / stats dashboard (shows completed, episodes watched, hours
  watched, favorite genres)
- Notifications for new episodes
- See friends' activity
- **Changing a nickname after it's been set** — v2 makes nicknames permanent
  by design; letting someone rename later is future work, not an oversight

## Security & Privacy (v2 additions)

- The account code needs the same entropy treatment `APP_PASSWORD` already
  gets (`openssl rand -hex 16` or similar) — it's the only thing standing
  between "anyone with the code" and that account.
- Store a hash of the code, never the code itself. Because codes are
  server-generated random tokens (not user-chosen passwords), a fast
  deterministic hash is defensible and allows an indexed lookup instead of
  iterating every user — see the technical design doc for the reasoning.
- Session cookies: HttpOnly, Secure, SameSite — signed/opaque tokens, not a
  guessable id.
- **Every server action needs its own auth check**, not just page components —
  this is already flagged in `scope.md`'s removal checklist and in
  `proxy.ts`'s comments, because actions are POST-able directly.
- `clearAllData()` must scope to the calling user only. In v1 it already only
  touches `TrackedShow`/`WatchedEpisode`/`Settings`, but now that those are
  shared tables across users, the `userId` filter is load-bearing, not
  incidental.
- Keep `APP_PASSWORD` in place until every route and action is session-checked
  and verified in production — do not jump ahead of the existing "Last step of
  Phase 2" checklist in `scope.md`.

## Assumptions & Open Risks

- iOS PWA behavior (install prompt, session/cookie persistence in standalone
  mode, splash screens) is the historically janky one — needs testing on an
  actual iPhone, not just Chrome DevTools' device emulation.
- `force-dynamic` pages mean the service worker's offline story is "app shell
  only." If that turns out to feel broken rather than merely limited, revisit
  before shipping rather than after.
- Nicknames are permanent by decision — a mistyped or regretted choice has no
  in-app fix in v2. Worth making sure the first-login UI is unambiguous about
  this being a one-time, irreversible choice before the user confirms.
