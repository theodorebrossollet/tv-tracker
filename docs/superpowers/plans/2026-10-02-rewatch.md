# Rewatch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an account start a show over (a fresh run, the old run kept as a read-only past run) and watch a movie again (the previous watch kept as a past watch), without changing how "current" progress, ratings, the Library or lists work.

**Architecture:** Archive-on-restart. `WatchedEpisode` keeps meaning the current run and `TrackedMovie` the current watch; three new additive history tables hold past runs and past watches. Two actions archive and clear in one database transaction using `INSERT … SELECT` plus `DELETE`/`UPDATE` in an array-form `$transaction`. Past data is read only by the title pages, and those reads fail softly.

**Tech Stack:** Next.js 16 App Router (server components, server actions), Prisma 7 on SQLite/Turso, vitest.

**Spec:** `docs/superpowers/specs/2026-10-02-rewatch-design.md`

**Before writing any Next.js code, read the relevant guide in `node_modules/next/dist/docs/`** (AGENTS.md: this is not the Next.js you know). Read AGENTS.md "Rules that will bite you" as well; the ones that apply are called out per task. Never run `next dev` (it regenerates a managed block in AGENTS.md that must not be committed).

## Global Constraints

- Nothing existing changes meaning: every query that reads `WatchedEpisode` / `TrackedMovie` keeps reading the CURRENT run/watch. Nothing may read the archive tables for current progress, finished/caught-up, Up Next or ratings. The Library, lists and dashboard code is not touched.
- Archive and clear happen in ONE database transaction (array-form `prisma.$transaction([...])`, as `clearAllData` does; use `$executeRaw` `INSERT … SELECT` for the copy so the copy and the delete see the same rows and a mark made mid-restart can never be deleted without being archived). Verify against the Prisma and adapter docs whether interactive transactions work before using them; the array form is the known-good one. A failure at any step leaves everything exactly as it was.
- `startShowOver(showId)`: refuses an untracked show, a show with no watched episodes (`"Nothing to start over."`), and a show already at `MAX_PAST_RUNS = 20` past runs; creates a `ShowRun` numbered highest-existing + 1 (unique per account and show), copies the caller's `WatchedEpisode` rows for that show's episodes into `ArchivedEpisodeWatch` (episodeId, watchedAt, rating as it was), deletes those rows, and sets the show's `TrackedShow.status` to `watching`.
- `watchMovieAgain(movieId)`: refuses a movie that is not the caller's or whose status is not `watched`, and one already at `MAX_PAST_WATCHES = 20`; creates a `PastMovieWatch` from the current `watchedAt` and `rating`, then sets `watchedAt` to now and `rating` to null; status stays `watched`.
- Ratings follow the current run/watch: after a restart the new run has no ratings and the Library "★" disappears until rated; past runs keep theirs. A past run's rating average uses the same season-then-show rule as the current one (`seasonAverage`/`showAverage` from `src/lib/ratings.ts`), computed in TypeScript over the archived rows joined to their episodes' season numbers.
- The current run number shown to the user is the number of past runs plus one ("Run N" in the header only when past runs exist).
- Every action starts with `requireOnboardedSession` above its `try`, validates every argument (non-string/odd inputs included) before any database access, scopes every Prisma/raw statement by `user.id`, and calls `revalidatePath("/", "layout")` on success. Every read through per-user data filters by `userId`; `Show`, `Episode` and `Movie` rows are shared between accounts, so any join to `WatchedEpisode`, `ArchivedEpisodeWatch` or `ShowRun` carries `userId` (AGENTS.md: a relation that is a list is always truthy).
- Title-page history reads (`pastRuns`, `pastWatches`) fail softly: on any error they are logged (`logger` + `describeError`) and returned as `null`, the sections are hidden, and the page renders. The two actions are not softened.
- "Clear all my data" also deletes the account's `ShowRun`s (their archived watches cascade) and `PastMovieWatch`es inside its existing transaction, scoped to the account.
- Components whose state the server can change derive from props with `useOptimistic`; client-only state (open sheet, confirmation step, error message) is `useState`; an error message is NEVER held in `useOptimistic` (it vanishes when the action settles). A server component never reads a plain value out of a `"use client"` module; `server-only` modules never reach client components.
- Dates for past runs/watches are formatted with `formatWatchedDate` (US Eastern, the app's convention for watch dates).
- One additive migration (three `CREATE TABLE`s); read the generated SQL: no table rebuilds. Generate it against a local file database only; never set `TURSO_AUTH_TOKEN` or a `libsql://` URL. The owner applies it to Turso before merge; this plan never touches production.
- Existing movie, show, rating, Library and list behaviour and tests must keep passing.

## Review Focus

- The archive and clear are atomic: a forced failure leaves the watched episodes exactly as they were, and there is no window where a mark is deleted without being archived. (Tasks 2, 3)
- Another account watching the same show or movie is never touched; run numbers are scoped per account and show. (Tasks 2, 3, 4)
- Restarting from each status (watching, watchlist, paused, stopped, finished) lands in `watching` at zero progress; every refusal holds (untracked, nothing watched, foreign or malformed id, the limits). (Task 2)
- A past run's average equals the season-then-show rule over archived rows; a run with no ratings shows no "★"; nothing renders "NaN"/"undefined". (Tasks 4, 6)
- If the new tables are missing, the show and movie pages still render without the history sections. (Task 4)
- Confirmation flows: cancel does nothing, confirm calls the action once, and an error message stays visible after the action settles. (Tasks 5, 7)
